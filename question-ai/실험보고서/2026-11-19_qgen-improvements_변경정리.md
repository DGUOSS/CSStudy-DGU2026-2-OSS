## 3. 변경 내용

### 3.1 속도 측정 (`llm.py`, `pipeline.py`)
- `logs.jsonl`: 호출마다 `sec`(전체), `wait_sec`(회사별 호출 간격 대기 + 일시 오류 재시도), `api_sec`(실제 모델 응답)
- 스키마 검증에 실패한 호출도 토큰·시간을 남김
- `summary.json`: `phase_sec`(교안 읽기·analyst·planner·문항), `item_sec`(문항별)

### 3.2 Solver 수정 (`schemas.py`, `prompts/solver.md`)
- `SolverOutput` 필드 순서를 `reasoning → answer`로. 모델이 JSON을 앞에서부터 쓰기 때문에 예전 순서에서는 **풀기 전에 답을 먼저 적음**
- 지시문: 계산 문제는 구간별로 적고 검산, answer는 reasoning의 결론과 같게

### 3.3 Reviewer 모델 (`config.yaml`)
- `gemini/gemini-3-flash-preview` → `anthropic/claude-haiku-5-5`
- judge도 haiku라 명세 §10(생성에 쓴 모델을 judge로 쓰지 말 것)과 겹침 → M5 전에 judge 교체 필요 (TODO 주석)

현재 모델 배치:

| 에이전트 | 모델 |
|---|---|
| analyst / planner / generator | Gemini (무료) |
| solver | `openai/gpt-5.4-mini` |
| reviewer | `anthropic/claude-haiku-5-5` |
| judge (M5용, 아직 안 쓰임) | `anthropic/claude-haiku-5-5` |

### 3.4 M1 검색 (`ingest/`, `scripts/build_index.py`)
- `ingest.py` → `ingest/` 패키지 (`pdf_parser`, `chunker`, `index`). pipeline·agents가 쓰는 함수 이름은 그대로
- **PDF 읽기**: 쪽별 글자 + 그림 표시. 쪽 면적 2% 미만 이미지는 글머리 기호·로고로 보고 무시 (실제 교안은 쪽마다 작은 이미지 10~20개)
- **글자 부족 쪽·스캔 PDF 경고** (예전에는 20자 미만 쪽을 말없이 버림)
- **쪽 제목**: 가장 큰 글씨로 추출. 예전에는 첫 줄이 쪽 번호라 planner 주제 목록이 "2", "3"이었음
- **청크**: 슬라이드 1장 = 1청크, 긴 쪽은 문단 단위로 나누고 뒷조각에 제목을 붙임 (예전 3000자 잘림 제거)
- **임베딩 검색**: `multilingual-e5-small`, `data/<과목>/index/`에 저장. 지문(해시)으로 오래된 인덱스를 감지하고 없거나 오래되면 BM25로 대신
- **검색어**: planner가 `source_titles`(교안 제목 목록에서 번역 없이 복사, 최대 3개)를 적고, 제목별 결과를 번갈아 합침. Bloom 수준은 검색어에서 뺌
- 그림 위주 쪽 PNG는 저장만 하고 **에이전트에게는 전달하지 않음** (이슈 #3에서 결정)

### 3.5 M2 출제 프로필 (`exam_profile.py`, `scripts/make_profile.py`)
- 기출·메모 줄마다 번호(`[E1.3]`, `[M1]`, 이미지 `[E2.p1]`)를 붙여 analyst에 보내고, **evidence가 실제 번호를 가리키는지 코드가 검사**. 한 괄호에 여러 번호(`[E1.2, E1.4]`)도 인정
- **기출·메모가 없으면 LLM 없이 기본 프로필** (객관식 0.4·단답형 0.2·서술형 0.4, 10문항, 근거·강조 주제 비움). 예전에는 없는 경향을 지어냄
- **사진 기출(png/jpg/jpeg/webp)과 글자 부족·그림 있는 PDF 쪽을 이미지로 analyst에 전송** (긴 변 1600px JPEG, 최대 12장, 저장 안 함). 예전에는 사진 기출을 말없이 무시
- `llm.call(images=...)`: LiteLLM 공통 `image_url` 형식. 캐시 키에는 이미지 해시만 넣어 글자만 보내는 호출의 캐시는 그대로 유지
- 기존 `profile.json`을 재사용할 때도 근거를 다시 검사

### 3.6 기타
- `Chunk.image_path`: 컴퓨터 전체 경로 → 과목 폴더 기준 상대 경로
- `run.py`: 출력을 UTF-8로. Windows 기본 콘솔(cp949)에서 `✗` 등 기호 출력 시 `UnicodeEncodeError`로 멈추던 문제
- `README.md`: 설치, 과목 자료, 인덱스, 실행, 검색 방식, 테스트
- `.gitignore`: 기출 사진 jpeg·webp 제외
- 설계 문서: "지엽적" 검색 규칙은 M3로 미룸

| 검색 방식 | 통과 |

| 3차 | 2차와 같음 | SOP 맞음, POS `(C+D')(B'+D)` **틀림**(m5), 스스로 모호·확신도 0.61 | 출제 POS가 최소 아님, 7리터럴 식 제시 → 수정 요청 (**맞음**) |

  - 결과: 수정 한도를 넘겨 문항 제외 → 최종 판단은 옳음 (끝까지 정답이 최소가 아니었음)
  - generator: 1차에 틀린 정답, 이후 "최소" 조건을 못 맞춤 / solver: POS 3번 모두 틀림 → 이 문제에서 검증자로 믿기 어려움 / reviewer: 출제 정답 판단은 매번 맞았으나 2차에서 풀이자의 틀린 POS를 올바르다고 봄
  - 이런 기계적으로 확인 가능한 계산(불 대수, 진수·부동소수점 변환)은 LLM 대신 **코드로 검산**하면 정확·빠름·무료 (명세 §6 규칙 기반 검사에 추가 후보)
- **병목 = q1의 reviewer**: q1 검토 평균 39.1초(호출당 1.3만~1.7만 토큰), 나머지 문항 8.8초. q1 한 문항이 에이전트 시간의 약 56%
- 영어 교안 실행보다 토큰이 2배 이상 많음

### 웹 연결 준비 (팀 확인 필요)
